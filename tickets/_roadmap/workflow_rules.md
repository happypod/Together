# Workflow Rules

이 문서는 백천마을 동행이동 OS의 설계, 작업지시서, 구현, 검증을 같은 기준으로 진행하기 위한 운영 규칙이다.

## 1. 기본 프로세스

모든 작업은 아래 순서를 따른다.

```text
사전설계 -> 정합성 -> 구현 -> 검증
```

순서를 건너뛰지 않는다. 급한 수정도 최소한의 사전설계와 정합성 확인을 티켓 또는 작업 로그에 남긴다.

### 1.1 사전설계

목표는 구현 전에 작업의 의미와 경계를 확정하는 것이다.

- 사용자 여정과 운영 시나리오를 확인한다.
- 관련 화면, API, 데이터 모델, 권한, AuditLog 범위를 적는다.
- 모바일/반응형 대상 여부를 확정한다.
- 고령 사용자 가독성과 명확성 기준을 확인한다.
- 개인정보, 민감정보, CSV, 영수증, 모바일 링크 영향을 확인한다.
- 결정되지 않은 사항은 open decision으로 남긴다.

### 1.2 정합성

목표는 기존 설계와 충돌하지 않게 만드는 것이다.

- `master_plan.md`의 MVP 범위와 충돌하지 않는지 확인한다.
- `definitions.md`의 용어, enum, 상태값, 권한과 일치하는지 확인한다.
- `design_style_guide.md`의 고령 사용자 가독성, 명확성, 접근성 기준과 충돌하지 않는지 확인한다.
- `queue.md`의 선행 티켓이 완료 또는 착수 가능한 상태인지 확인한다.
- 제외 기능을 우회 구현하지 않는지 확인한다.
- 기존 데이터 모델과 마이그레이션 영향이 있는지 확인한다.

### 1.3 구현

목표는 사전설계와 정합성 기준대로 작게 구현하는 것이다.

- 티켓 범위 밖 리팩터링을 섞지 않는다.
- 권한 검증은 서버에서 수행한다.
- 모바일 우선 UI를 기본으로 만들고 데스크톱에서 확장한다.
- UI는 밝고 가독성이 높으며 고령 사용자가 실수 없이 이해할 수 있게 만든다.
- 상태 변경, 정산 수정, CSV 내보내기, 토큰 발급, 파일첨부는 AuditLog를 고려한다.
- 구현 중 새 결정이 필요하면 `decisions.md` 또는 티켓에 기록한다.

### 1.4 검증

목표는 사용자 흐름, 데이터, 권한, 반응형 레이아웃이 실제로 동작하는지 확인하는 것이다.

- 기능 검증: 주요 happy path와 실패 경로를 확인한다.
- 데이터 검증: 필수값, enum, 상태 전이, 정산 산식을 확인한다.
- 권한 검증: 허용 사용자와 차단 사용자를 모두 확인한다.
- 개인정보 검증: 목록 마스킹, CSV 권한, 민감정보 입력 제한을 확인한다.
- 반응형 검증: 모바일, 태블릿, 데스크톱에서 레이아웃 깨짐을 확인한다.
- 디자인 검증: 글자 크기, 대비, 터치 대상, 쉬운 문구, 오류 안내를 확인한다.

## 2. 작업지시서 표준 포맷

모든 신규 티켓과 큰 변경 작업은 `_templates/ticket.md` 포맷을 따른다.

필수 섹션:

- 메타
- 목표
- 배경
- 사용자와 화면
- 범위
- 제외
- 사전설계
- 정합성
- 모델별 지시
- 구현
- 완료 기준
- 검증 기록

섹션명은 임의로 바꾸지 않는다. 내용이 해당 없으면 `not_applicable` 또는 `해당 없음`으로 표시한다.

## 3. 모델별 지시 작성 규칙

작업지시서는 여러 역할 또는 에이전트가 같은 문맥을 이해할 수 있어야 한다. 아래 항목 중 관련 있는 지시는 반드시 적는다.

### Product/PM

- 사용자가 누구인지
- 어떤 운영 문제를 해결하는지
- 무엇을 완료로 볼지
- 제외해야 할 기능이 무엇인지

### Data

- 변경되는 모델과 필드
- 관계와 제약
- enum과 상태값
- seed와 migration 영향
- 인덱스 또는 조회 성능 고려

### Backend

- Server Action/API 이름
- 입력값과 출력값
- 권한 검사
- 입력 검증
- AuditLog 기록
- 오류 처리

### Frontend

- 대상 화면과 라우트
- 밝고 가독성 높은 디자인 스타일
- 모바일 우선 레이아웃
- 반응형 breakpoint
- 빈 상태, 로딩 상태, 오류 상태
- 폼 검증, 터치 대상, 긴 텍스트 처리

### QA

- 검증할 사용자 흐름
- 권한별 테스트
- 상태 전이 테스트
- 개인정보와 민감정보 테스트
- 모바일/태블릿/데스크톱 화면 테스트
- 고령 사용자 기준의 글자 크기, 대비, 버튼 크기, 오류 문구 테스트

### Ops

- 환경변수
- 배포 영향
- 로그와 모니터링
- 백업 또는 데이터 보존
- 운영 설정 변경

## 4. 모바일 우선 설계 원칙

백천마을 동행이동 OS는 관리자 웹 중심이지만 현장 운영, 동행링커 입력, 귀가확인, 만족도 입력은 모바일 활용성이 중요하다. 따라서 모든 화면은 모바일 사용 가능성을 먼저 확인한다.

### 4.1 대상 화면 분류

| 분류 | 설명 | 모바일 기준 |
| --- | --- | --- |
| Admin Core | 관리자 홈, 목록, 상세, 정산 | 읽기와 핵심 조작 가능 |
| Field Input | 모바일 링크형 입력폼, 귀가확인, 만족도 | 모바일 최우선 |
| Dense Ops | 그룹 편성, 월간 리포트, CSV | 모바일 조회 가능, 복잡 편집은 데스크톱 최적 |
| System | 권한, 설정, AuditLog | 모바일 조회 가능, 데스크톱 편집 우선 |

### 4.2 Breakpoint 기준

- `mobile-sm`: 360px
- `mobile`: 390px
- `tablet`: 768px
- `desktop`: 1024px
- `wide`: 1280px 이상

구현 검증은 최소 360px, 390px, 768px, 1280px에서 수행한다.

### 4.3 레이아웃 규칙

- 모바일은 단일 컬럼을 기본으로 한다.
- 데스크톱은 목록/상세 또는 요약/작업 패널을 2컬럼 이상으로 확장할 수 있다.
- 모바일 하단에는 핵심 저장 또는 확인 버튼을 명확히 배치한다.
- 테이블은 모바일에서 카드형 목록, 행 확장, 가로 스크롤 중 하나로 전환한다.
- 긴 이름, 긴 마을명, 긴 목적지는 줄바꿈 또는 말줄임 기준을 정한다.
- 버튼 텍스트는 줄바꿈되더라도 버튼 높이가 과도하게 커지지 않게 한다.
- 상태 배지는 색상과 텍스트를 함께 사용한다.
- 모달은 모바일에서 전체 화면 또는 하단 시트로 전환한다.
- 폼은 한 화면에 너무 많은 필드를 몰아넣지 않고 섹션 단위로 나눈다.

### 4.4 터치와 입력 규칙

- 주요 터치 대상은 최소 44px 높이를 권장한다.
- 전화번호, 날짜, 시간대, 금액 입력은 모바일 키보드 유형을 맞춘다.
- 필수 체크박스는 라벨 전체가 터치 가능해야 한다.
- 저장 실패 시 오류 위치로 스크롤하거나 명확한 오류 요약을 보여준다.
- 모바일 링크형 폼은 로그인 없이도 현재 입력 대상과 만료 상태를 명확히 보여준다.

### 4.5 정보 밀도 규칙

- 모바일 첫 화면에는 오늘 해야 할 작업, 상태, 다음 행동을 우선 배치한다.
- 주민 개인정보는 모바일 목록에서 더 엄격하게 마스킹한다.
- 관리자 대시보드의 KPI 카드는 모바일에서 2열 또는 1열로 접히며 내용이 잘리지 않아야 한다.
- 정산 금액은 숫자 정렬과 단위 표시를 일관되게 유지한다.

### 4.6 고령 사용자 디자인 원칙

- 모든 UI 작업은 `design_style_guide.md`를 따른다.
- 작은 글자, 낮은 대비, hover 전용 조작, 아이콘만 있는 핵심 버튼을 피한다.
- 주요 작업 버튼은 충분히 크고 문구가 명확해야 한다.
- 오류와 경고는 색상만이 아니라 제목과 설명으로 이해 가능해야 한다.
- 화면은 밝고 단순해야 하며, 현재 상태와 다음 행동이 상단에서 바로 보여야 한다.

## 5. 반응형 검증 체크리스트

각 UI 티켓은 아래 항목을 검증 기록에 남긴다.

- [ ] 360px에서 좌우 스크롤 없이 핵심 작업이 가능하다.
- [ ] 390px에서 주요 버튼과 입력 필드가 겹치지 않는다.
- [ ] 768px에서 목록과 상세의 전환이 자연스럽다.
- [ ] 1280px 이상에서 정보가 과도하게 흩어지지 않는다.
- [ ] 긴 텍스트, 긴 연락처, 긴 목적지가 레이아웃을 깨지 않는다.
- [ ] 키보드가 열린 모바일 입력 상황에서 저장 버튼 접근이 가능하다.
- [ ] 로딩, 빈 상태, 오류 상태가 모바일과 데스크톱 모두에서 확인된다.
- [ ] 고령 사용자 기준의 글자 크기, 대비, 버튼 크기, 쉬운 문구가 확인된다.

## 6. 작업 완료 판정

작업은 코드가 작성되었다는 이유만으로 완료하지 않는다. 아래 조건을 만족해야 `done`으로 바꿀 수 있다.

- 사전설계가 남아 있다.
- 정합성 확인이 남아 있다.
- 구현 범위가 티켓과 일치한다.
- 검증 기록이 남아 있다.
- 모바일/반응형 대상이면 viewport 검증이 남아 있다.
- UI 대상이면 `design_style_guide.md` 검증이 남아 있다.
- 필요한 경우 `queue.md`, `status.json`, `decisions.md`가 갱신되어 있다.
