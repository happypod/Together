# 백천마을 동행이동 OS MVP Master Plan

- 작성일: 2026-05-30
- 기준 문서: 첨부 설계문서 `백천마을 동행이동 OS MVP 설계문서`
- 공식명: 백천마을 동행이동 OS
- 주민 홍보명: 백천마을 동행택시
- 시스템 성격: 공동예약형 생활이동 및 동행링커 운영관리 시스템
- 1차 구현 범위: 관리자 웹 중심 MVP, 모바일 링크형 입력폼 보조

## 1. 제품 목적

백천마을 동행이동 OS는 소원권역 어촌신활력증진사업의 사회혁신프로그램 운영을 위한 내부 운영관리 시스템이다. 주민협의체와 앵커조직이 주민 생활이동 신청을 접수하고, 주민 최대 3명 단위의 공동예약 그룹을 구성하며, 동행링커 배정, 택시연합 예약요청, 운행상태, 귀가확인, 정산, 만족도, 월간 성과를 관리한다.

이 시스템은 공개 모빌리티 플랫폼이 아니다. 일반 주민은 복잡한 회원가입 앱이 아니라 신청 링크 또는 현장 운영자 입력을 통해 접근한다.

## 2. MVP 범위

### 포함

- 관리자 홈 및 KPI 요약
- 주민 이동 신청 등록, 목록, 필터
- 이동 캘린더
- 공동예약 그룹 생성 및 상태 관리
- 동행링커 등록, 배정, 활동상태 관리
- 택시연합 예약요청 및 확정 정보 기록
- 운행상태 및 귀가확인 기록
- 정산 산식 적용 및 영수증 기록
- 만족도, 특이사항, 사고, 민원 기록
- 월간 리포트 및 CSV 내보내기
- 역할 기반 접근 제어
- AuditLog 기록

### 제외

- 공개 사용자 앱스토어 앱
- 불특정 다수 가입 구조
- 시스템 자동 차량 배정
- 외부 차량 요청 API 연동
- 자동 결제 및 카드 결제
- 실시간 좌표 기반 이동 추적
- 기사 전용 별도 앱
- AI 경로 최적화
- 의료상담 또는 전문 이송 업무
- 건강 민감 세부정보 수집
- PDF 출력 자동화

```text
REQUESTED
-> RECRUITING
-> GROUP_READY
-> LINKER_RECRUITING
-> LINKER_ASSIGNED
-> TAXI_REQUESTED
-> TAXI_CONFIRMED
-> IN_PROGRESS
-> RETURN_CONFIRMED
-> SETTLED
-> REPORTED
```

취소와 예외 상태는 관리자 권한으로만 처리하며, 사유 입력과 AuditLog 기록이 필수다.

## 8. 구현 기준 스택

구체 repo가 아직 비어 있으므로, MVP 제작 시작 시 아래 구성을 기본안으로 둔다.

- Web: Next.js App Router, TypeScript
- UI: Tailwind CSS 기반의 관리형 대시보드 컴포넌트
- DB: PostgreSQL 또는 Supabase Postgres
- ORM: Prisma
- Auth: 역할 기반 접근 제어를 지원하는 세션 기반 인증
- File/Receipt: MVP에서는 파일 업로드 또는 외부 링크 필드 중 하나로 시작
- Deployment: Vercel

스택 변경 시 `decisions.md`에 결정 사유를 남긴다.

## 11. 정산 산식

### 기본

```text
residentPerPersonShare = totalFare / residentCount
residentTotalShare = residentPerPersonShare * residentCount
anchorSupportAmount = totalFare - residentTotalShare
```

### 시범기

```text
residentTotalShare = 0
anchorSupportAmount = totalFare
residentPerPersonShare = 0
```

### 자립전환기

```text
residentTotalShare = totalFare
anchorSupportAmount = 0
residentPerPersonShare = totalFare / residentCount
```

### 취약계층 지원

```text
supportFromCommunityFund = selectedSupportAmount
residentTotalShare = totalFare - supportFromCommunityFund
residentPerPersonShare = residentTotalShare / residentCount
```

검증 기준:

- `residentCount`는 1 이상이어야 한다.
- 원 단위 반올림 또는 절사 정책을 구현 전 확정한다.
- 상생기금은 택시요금 차감 또는 주민요금 환급으로 표시하지 않는다.
- 정산 완료 후 수정은 관리자 권한과 수정 사유가 필요하다.

## 12. 완료 기준

완료 기준은 두 단계로 나눈다. P0는 실제 운영이 가능한 핵심 MVP이고, P1까지 포함해야 1차 설계문서의 전체 MVP 범위가 닫힌다.

### P0 Operational MVP 완료 기준

P0 Operational MVP 완료는 아래 조건을 만족해야 한다.

- P0 티켓이 모두 `done` 상태다.
- TypeScript 타입 오류가 없다.
- DB 스키마 검증이 통과한다.
- 권한별 접근 제어가 서버에서 검증된다.
- 개인정보와 민감정보 제한이 UI와 모델에 반영된다.
- 상태 전이와 AuditLog가 주요 변경에 적용된다.
- 대시보드 핵심 KPI가 실제 데이터 기준으로 생성된다.
- 제외 기능이 UI 문구나 메뉴에 노출되지 않는다.

### Full 1차 MVP 완료 기준

Full 1차 MVP 완료는 아래 조건을 추가로 만족해야 한다.

- P1 티켓이 모두 `done` 상태다.
- 이동 캘린더가 월간, 주간, 일간 기준으로 조회된다.
- 모바일 링크형 입력폼이 실제 운영 흐름에서 검증된다.
- 월간 리포트와 CSV가 실제 데이터 기준으로 생성된다.
- 만족도, 사고, 민원, 동행링커 활동통계가 월간 리포트에 반영된다.

## 13. 보완 검토 결과

초기 마스터플랜은 MVP 범위와 큰 기능 흐름을 정리하기에는 충분하다. 다만 제작자가 바로 구현에 들어가면 아래 영역에서 설계 공백이 생길 수 있으므로 본 문서에 보완 기준을 추가한다.

### 보완이 필요한 영역

| 영역 | 기존 상태 | 보완 방향 |
| --- | --- | --- |
| 인증과 사용자 모델 | 권한 역할은 있으나 `User` 모델 기준이 약함 | `User`, 역할, 세션, 초대, 비활성화 기준 추가 |
| 모바일 링크형 입력 | 기능명만 있음 | 토큰 발급, 만료, 1회성 여부, 입력 가능 범위 정의 |
| 파일과 영수증 | 링크 또는 첨부 수준 | `FileAttachment`, 파일 종류, 크기, 접근권한 기준 추가 |
| 운영 연락 기록 | 신청과 예약 기록 중심 | 주민, 링커, 택시연합 연락 확인을 `ContactLog`로 보조 |
| 설정값 | 기본 요금과 주민 수가 문서에 고정 | `AppSetting`으로 기본요금, 정산 반올림, 마을, 시간대 관리 |
| 리포트 지표 | KPI 목록은 있으나 산식 부족 | 월간 지표 계산 기준과 CSV 컬럼 기준 추가 |
| 데이터 검증 | 필드 목록 중심 | 중복, 상태 전이, 그룹 인원, 정산 잠금 검증 규칙 추가 |
| 운영과 배포 | 스택 수준 | 환경, 백업, 로그, 장애 대응, 릴리즈 게이트 추가 |

### MVP에 추가해야 할 기능

아래 기능은 범위 확장이 아니라 운영 안정성을 위한 기반 기능으로 본다.

- 사용자 계정과 역할 관리의 최소 구현
- 모바일 링크 토큰 발급, 만료, 사용 범위 제한
- 영수증과 첨부파일의 공통 메타데이터 관리
- 운영 연락 이력 기록
- 기본요금, 정산 반올림 정책, 마을명, 시간대의 운영 설정
- 월간 리포트 지표 산식 고정
- CSV 내보내기 감사로그와 다운로드 사유 기록
- 정산 완료 후 수정 잠금과 관리자 수정 사유 기록

아래 기능은 P1 또는 P2로 미루며 P0 구현에 섞지 않는다.

- 문자, 카카오톡, 알림톡 자동 발송
- 외부 택시 API 연동
- 대량 CSV 가져오기 자동화
- PDF 보고서 자동 생성
- 자동 배차 또는 경로 추천

## 14. 핵심 사용자 여정

### 운영자 신청 접수 여정

1. 운영자가 주민 또는 보호자 연락을 받고 주민 정보를 확인한다.
2. 운영자가 이동 희망일, 시간대, 목적, 출발지, 목적지를 입력한다.
3. 개인정보 동의, 제3자 제공 동의, 민감정보 미수집 확인을 체크한다.
4. 신청은 `REQUESTED` 상태로 저장된다.
5. 운영자는 신청 목록에서 날짜, 마을, 목적, 상태로 필터링한다.

### 공동예약 그룹 구성 여정

1. 운영자가 유사 날짜, 방향, 시간대 신청을 확인한다.
2. 주민 1명 이상 3명 이하를 선택해 그룹을 생성한다.
3. 픽업 순서, 픽업 장소, 예정시간, 목적지 요약을 입력한다.
4. 그룹 상태가 `GROUP_READY`까지 진행된다.
5. 그룹 인원이 3명을 초과하면 서버에서 저장을 거부한다.

### 동행링커와 택시예약 여정

1. 운영자가 활동 가능한 동행링커를 그룹에 배정한다.
2. 택시연합 예약요청 시간을 기록한다.
3. 택시연합 담당자 또는 운영자가 예약 확정 정보를 입력한다.
4. 차량번호, 기사 연락처, 예상요금 또는 실제요금을 기록한다.
5. 예약 확정 후 그룹 상태가 `TAXI_CONFIRMED`로 진행된다.

### 운행과 귀가확인 여정

1. 동행링커 또는 운영자가 링커 탑승을 확인한다.
2. 주민별 탑승 확인을 기록한다.
3. 목적지 도착과 생활업무 수행 확인을 기록한다.
4. 귀가 출발과 주민별 귀가확인을 기록한다.
5. 전체 귀가확인이 끝나면 `RETURN_CONFIRMED`로 진행된다.

### 정산과 월간 보고 여정

1. 운영자가 실제 택시요금과 영수증을 기록한다.
2. 시스템이 정산 모드에 따라 주민 분담액과 앵커 지원금을 계산한다.
3. 관리자가 정산 완료 처리한다.
4. 정산 완료 후 수정은 관리자 권한과 수정 사유가 필요하다.
5. 월간 리포트는 실제 운행 완료 및 정산 데이터를 기준으로 집계한다.

## 16. 데이터 검증과 업무 규칙

### 공통 검증

- 이름은 공백 제거 후 저장하며 빈 문자열은 허용하지 않는다.
- 연락처는 국내 전화번호 형식을 기본으로 하되 하이픈 유무를 허용한다.
- 날짜와 시간대는 과거 입력을 경고하고, 저장 허용 여부는 운영자 권한으로 제한한다.
- 상세 메모에는 주민등록번호, 진단명, 처치 내용, 상담 내용 입력을 금지하는 안내를 표시한다.
- 삭제는 기본적으로 soft delete 또는 비활성화로 처리하고 AuditLog를 남긴다.

### 신청 검증

- 신청 생성 시 개인정보 동의, 제3자 제공 동의, 민감정보 미수집 확인이 모두 필요하다.
- 한 주민이 같은 날짜와 시간대에 중복 신청을 만들면 중복 경고를 표시한다.
- 이미 운행이 시작된 신청은 그룹 변경을 제한한다.

### 그룹 검증

- 그룹 멤버는 1명 이상 3명 이하만 허용한다.
- 같은 신청은 두 개 이상의 활성 그룹에 들어갈 수 없다.
- 픽업 순서는 그룹 내에서 중복될 수 없다.
- `IN_PROGRESS` 이후 멤버 제거는 예외 상태와 사유가 필요하다.

### 택시예약 검증

- 택시예약 요청은 그룹이 확정되고 동행링커 배정이 끝난 뒤 가능하다.
- 예약 확정 시 차량번호 또는 확정 확인 메모 중 하나는 필요하다.
- 기사 연락처는 택시 파트너와 관리자 상세 화면에서만 전체 표시한다.

### 운행 검증

- 귀가확인은 주민별로 기록한다.
- 전체 귀가확인 시점은 모든 활성 멤버의 귀가확인이 끝난 뒤 저장한다.
- 미탑승 또는 일부 완료는 예외 사유를 필수로 남긴다.

### 정산 검증

- 총 택시요금은 0 이상 정수로 저장한다.
- 주민 수는 활성 그룹 멤버 수를 기본값으로 사용한다.
- 정산 반올림 정책은 `AppSetting`의 `fareRoundingPolicy`를 따른다.
- 정산 완료 후 수정은 `SUPER_ADMIN` 또는 `ANCHOR_ADMIN`만 가능하며 수정 사유가 필요하다.
- 상생기금은 택시요금 차감액으로 표시하지 않는다.

## 17. 보안, 개인정보, 모바일 링크

### 인증과 세션

- 모든 관리자 화면은 로그인 후 접근한다.
- 사용자는 하나 이상의 역할을 가진다.
- 비활성화된 사용자는 로그인과 API 호출을 할 수 없다.
- 세션 만료와 재로그인 정책은 구현 전 확정한다.

### 개인정보 표시

- 목록 화면은 연락처를 마스킹한다.
- 상세 화면은 권한이 있는 사용자만 전체 연락처를 볼 수 있다.
- CSV 내보내기는 권한, 사유, AuditLog가 필요하다.
- AuditLog에는 필요 이상의 개인정보 원문을 저장하지 않는다.

### 모바일 링크형 입력폼

- `MobileFormToken`은 대상 엔티티, 허용 action, 만료시간, 사용 횟수 제한을 가진다.
- 링크는 로그인 없는 보조 입력에만 사용하고 관리자 전체 화면 접근 권한을 부여하지 않는다.
- 기본 만료시간은 24시간으로 두며, 운영 설정으로 변경 가능하게 한다.
- 토큰 제출 시 IP 또는 user agent 등 최소 접근 맥락을 AuditLog에 남긴다.
- 토큰으로 입력 가능한 필드는 배정 건 운행상태, 귀가확인, 만족도 등 제한 범위로 한정한다.

### 파일과 영수증

- 영수증은 `FileAttachment` 또는 외부 링크로 기록한다.
- 허용 파일 형식은 이미지와 PDF로 제한한다.
- 파일 크기 제한은 구현 전 확정하되 기본 10MB 이하를 권장한다.
- 영수증 첨부 화면에는 불필요한 개인정보가 포함되지 않도록 안내한다.

### 보관과 삭제

- 보관기간은 운영 정책 확정 전까지 설정값으로 분리한다.
- 삭제 요청은 실제 삭제보다 비활성화, 익명화, 접근 제한을 우선 검토한다.
- 정산과 감사 목적 데이터는 임의 삭제하지 않고 관리자 승인 절차를 둔다.

## 18. 리포트 지표 정의

월간 리포트는 `serviceDate` 또는 운행 완료일을 기준으로 한다. 기준일은 구현 전 하나로 확정하고 `AppSetting.reportDateBasis`에 기록한다.

| 지표 | 계산 기준 |
| --- | --- |
| 월 운행건수 | 해당 월 `RETURN_CONFIRMED` 이상 그룹 수 |
| 월 이용 주민 수 | 해당 월 운행 완료 그룹의 고유 주민 수 |
| 누적 이용 주민 수 | 서비스 시작 이후 운행 완료 그룹의 고유 주민 수 |
| 월 동행링커 활동건수 | 해당 월 링커가 배정된 운행 완료 그룹 수 |
| 활동 동행링커 수 | 해당 월 1건 이상 배정된 링커 수 |
| 평균 택시요금 | 해당 월 정산 완료 건의 `totalFare` 평균 |
| 총 이동지원비 | 해당 월 `anchorSupportAmount` 합계 |
| 주민 1인 평균 분담액 | 해당 월 `residentPerPersonShare` 평균 |
| 사고·민원 건수 | 해당 월 `IncidentReport` 수 |
| 만족도 평균 | 해당 월 만족도 항목 평균 |
| 상생기금 조성액 | 해당 월 `CommunityFund`의 `CONTRIBUTION` 합계 |

CSV 내보내기는 월간 리포트 요약 CSV와 운행 상세 CSV를 분리한다. 운행 상세 CSV에는 권한에 따라 연락처 전체 또는 마스킹 값을 사용한다.

## 19. 화면 품질과 UX 기준

- 관리자 화면은 반복 업무에 맞게 정보 밀도를 높이고 과도한 홍보형 레이아웃을 쓰지 않는다.
- 고령 사용자를 고려해 밝고 가독성이 높은 화면을 기본으로 한다.
- 화면의 최우선 기준은 명확한 UI/UX, 실수 방지, 빠른 확인이다.
- 모든 목록은 빈 상태, 로딩 상태, 오류 상태를 가진다.
- 필수 입력 누락, 권한 없음, 상태 전이 실패는 사용자가 다음 행동을 알 수 있는 문구로 표시한다.
- 모바일 우선 설계를 기본으로 하고, 데스크톱에서는 정보 밀도와 다중 패널을 확장한다.
- 모바일 입력폼은 작은 화면에서 한 손 입력이 가능하도록 필드를 짧게 나누고 저장 버튼을 명확하게 둔다.
- 의료상담, 환자 이송, 치료, 진단, 자동 배차, 할인, 환급처럼 MVP 성격을 오해시킬 수 있는 표현을 쓰지 않는다.
- 주요 작업 버튼은 저장, 배정, 예약요청, 확정, 귀가확인, 정산완료처럼 운영 동사로 통일한다.

### 디자인 스타일 기준

디자인의 세부 기준은 `design_style_guide.md`를 따른다.

핵심 방향:

- 밝은 중립 배경과 흰색 작업 영역을 사용한다.
- 본문 기본 글자 크기는 모바일 17px 이상, 고령자 직접 입력 화면은 18px 이상을 우선한다.
- 주요 버튼은 모바일에서 48px 이상 높이를 권장한다.
- 중요한 상태와 오류는 색상만으로 표현하지 않고 텍스트를 함께 사용한다.
- 목록은 모바일에서 카드형으로 전환하고 개인정보는 마스킹한다.
- 오류 메시지는 원인과 다음 행동을 함께 알려준다.
- 복잡한 장식, 과한 그라데이션, 작은 글자, 낮은 대비, hover 전용 핵심 기능을 금지한다.

### 모바일/반응형 설계 기준

| Viewport | 기준 |
| --- | --- |
| 360px | 최소 모바일 폭. 핵심 입력과 저장이 좌우 스크롤 없이 가능해야 한다. |
| 390px | 일반 모바일 폭. 목록 카드와 폼이 안정적으로 보여야 한다. |
| 768px | 태블릿 폭. 목록과 상세 또는 요약과 작업 영역을 나눌 수 있다. |
| 1024px | 데스크톱 시작점. 운영자용 정보 밀도를 높인다. |
| 1280px 이상 | 넓은 화면. 대시보드와 그룹 상세의 보조 패널을 확장한다. |

모바일 레이아웃 규칙:

- 모바일은 단일 컬럼을 기본으로 한다.
- 테이블은 모바일에서 카드형 목록, 행 확장, 또는 제한된 가로 스크롤로 전환한다.
- 주요 터치 대상은 최소 44px 높이를 권장한다.
- 필수 작업 버튼은 화면 하단 또는 폼 끝에서 명확하게 접근 가능해야 한다.
- 긴 주민명, 마을명, 목적지, 메모는 줄바꿈 또는 말줄임 기준을 가진다.
- 상태는 색상만으로 표현하지 않고 텍스트를 함께 표시한다.
- 모달은 모바일에서 전체 화면 또는 하단 시트로 전환한다.
- 모바일 링크형 폼은 로그인 없는 제한 입력이므로 대상, 만료, 저장 결과를 명확히 보여준다.

화면별 모바일 우선순위:

| 화면 | 모바일 기준 |
| --- | --- |
| 모바일 링크형 입력폼 | 모바일 최우선. 360px에서 전체 입력 가능해야 한다. |
| 귀가확인, 운행상태 입력 | 모바일 최우선. 터치와 저장 실패 처리가 명확해야 한다. |
| 주민 신청 등록 | 모바일 사용 가능. 필수 동의와 개인정보 안내가 잘 보여야 한다. |
| 신청 목록, 그룹 목록 | 모바일 조회 가능. 테이블은 카드형으로 전환한다. |
| 그룹 상세, 정산 | 모바일 조회와 핵심 조작 가능. 복잡 편집은 데스크톱에서 더 편해야 한다. |
| 월간 리포트, CSV | 모바일 조회 가능. 내보내기와 상세 분석은 데스크톱 우선이다. |

## 19.1 작업지시서와 진행 순서

모든 작업지시서는 `_templates/ticket.md` 포맷을 따른다. 작업 순서는 아래를 기본으로 한다.

```text
사전설계 -> 정합성 -> 구현 -> 검증
```

- 사전설계: 사용자 여정, 데이터 모델, 권한, AuditLog, 모바일 영향을 확인한다.
- 정합성: `master_plan.md`, `definitions.md`, `queue.md`, MVP 제외 범위와 충돌하지 않는지 확인한다.
- 구현: 티켓 범위 안에서 작게 구현하고, 서버 권한 검증과 입력 검증을 적용한다.
- 검증: 기능, 권한, 개인정보, 상태 전이, 정산 또는 리포트 산식, 모바일/반응형 레이아웃을 확인한다.

모델별 지시는 Product/PM, Data, Backend, Frontend, QA, Ops 섹션으로 나눠 작성한다. 해당 없는 섹션은 `해당 없음`으로 표시하되 섹션 자체는 유지한다.

## 20. 비기능 요구사항과 운영 기준

### 성능

- P0 목록 화면은 기본 페이지네이션을 사용한다.
- 검색과 필터는 DB 인덱스를 고려한다.
- 대시보드 KPI는 필요 시 캐시하거나 월간 집계 테이블을 사용한다.

### 접근성

- 폼 라벨, 오류 메시지, 키보드 이동을 지원한다.
- 색상만으로 상태를 구분하지 않고 텍스트 상태명을 함께 표시한다.
- 모바일 입력폼의 터치 대상은 충분한 크기로 둔다.
- 브라우저 줌 125%에서도 핵심 작업이 가능해야 한다.
- 아이콘만 있는 버튼은 `aria-label` 또는 tooltip을 제공한다.

### 환경과 배포

- 개발, 스테이징, 운영 환경을 분리한다.
- `.env.example`에는 필요한 환경변수와 설명을 둔다.
- 운영 배포 전 DB migration, seed, rollback 방안을 확인한다.
- 배포 전 `lint`, `typecheck`, `build`, schema validation을 통과해야 한다.

### 백업과 장애 대응

- 운영 DB는 정기 백업 정책을 둔다.
- CSV 내보내기는 백업 수단이 아니라 보고와 검토 수단으로만 사용한다.
- 장애 발생 시 최근 AuditLog와 배포 버전을 확인할 수 있어야 한다.

### 관측과 로그

- 서버 오류는 사용자에게 민감정보 없이 표시한다.
- 관리자 작업 실패는 원인 추적이 가능하도록 서버 로그에 남긴다.
- AuditLog는 운영 행동 추적용이고, 디버그 로그와 분리한다.

## 21. 릴리즈 게이트

P0 릴리즈 전 아래 조건을 모두 확인한다.

- 프로젝트 스택과 DB 연결 방식이 `decisions.md`에 확정되어 있다.
- `User`, RBAC, AuditLog, MobileFormToken, FileAttachment의 최소 모델이 존재한다.
- P0 화면이 모두 접근 가능하고 빈 상태와 오류 상태를 가진다.
- 서버 권한 검증이 UI 숨김과 별도로 동작한다.
- 연락처 마스킹, CSV 권한, 감사로그가 검증된다.
- 정산 산식과 반올림 정책이 확정되어 테스트된다.
- 모바일 링크는 만료시간과 입력 가능 범위 제한을 가진다.
- 모바일/반응형 대상 화면은 360px, 390px, 768px, 1280px 이상에서 검증 기록이 남아 있다.
- UI 대상 화면은 `design_style_guide.md`의 고령 사용자 가독성, 대비, 터치 대상 기준을 검증했다.
- 작업지시서는 사전설계, 정합성, 구현, 검증 순서를 따른다.
- 제외 기능이 메뉴, 버튼, 설명 문구에 노출되지 않는다.

상세 gate는 `quality_gates.md`를 기준으로 한다. 구현 모듈과 route/service 경계는 `implementation_blueprint.md`를 따른다.
